natural compact · the handoff agent

One agent. Two ways to continue.

The scribe model is the only model call in the whole feature. This is what wakes it, the exact prompts it gets, what it returns — and the answer to the question that decides the design: you can keep the same chat, and Pi gives you the hooks to do it.

02 · the trigger

Nothing wakes the agent except a human opening the review

lazy by design

Thresholds and boundaries only produce an offer. The scribe is invoked at the moment the human asks to see the handoff, so a declined offer costs zero tokens and touches nothing.

1
Eligible
62% of window, idle, no queued work, stable snapshot.
2
Boundary verified
Model proposes; decision-server through Jev confirms and names the work type.
3
Offer accepted
The human chooses to review. This is the only input that costs anything.
4
Agent invoked
One read-only call, bounded in input size and latency.
5
Review
Edit, approve, or decline. Decline returns to the loop untouched.

What the agent cannot do: start a turn, write a file, run a command, or decide whether to continue. Its output is text in a template, and both continuations treat that text as untrusted until a human approves it.

03 · the call

System prompt, user prompt, output

one call

The material is split so the transcript can never impersonate an instruction. The system prompt carries policy; the user prompt carries data, labelled as data.

// system — proposed draft, shipped with the extension
You write the handoff note that lets work continue in a fresh context.

Rules
- You are read-only. You cannot edit files, run commands, or start turns.
- Use only the material below and files listed as readable.
- Never claim a test ran, a build passed, or a decision was made unless
  the transcript shows it. Quote what the transcript shows.
- Preserve uncertainty and open questions. Do not resolve them.
- Reproduce the pending request verbatim. Do not rewrite, summarize,
  shorten, or re-quote it.
- Refer to the previous session by the link you are given.
- Output only the template for the requested mode. No preamble.

Modes
- new:      decisions, constraints, project context, pending request, link
- ongoing:  goal, decisions, constraints, files, changes, tests, blockers,
            next steps, open questions, pending request, link

Hard limit
- Stay within the character budget. Prefer dropping detail over dropping
  a constraint, a blocker, or an unresolved question. Always keep the
  file blocks Pi uses to track reads and edits.

The read-only sentence is a capability, not a request: the call has no mutating tools available at all.

mode
ongoing — decided by the judge, not by this agent. It picks the template, not the input.
pending request
verbatim, fenced and labelled as data: “run the migration on staging and paste the plan output”.
branch projection
Active branch only, no abandoned branches. Oldest turns elided first; tool output truncated to head and tail; bounded to a configured cap.
compaction summary
If Pi already compacted, that summary is included as prior context, so the new note cannot contradict it.
referenced files
Optional and bounded: only files the transcript referenced, through a read-only interface, quoted and marked untrusted.
delimiters
Transcript and file text are wrapped as data. Instructions smuggled inside them are not instructions.

Assembled by the extension, not by a model: the same transcript yields the same prompt, so the call is reproducible and testable.

Both templates carry the two things that must never be lost: the way back, and the pending request verbatim.

tools offered
none by default. File access, if enabled, is a read-only interface with a path allow-list and a byte cap — never a shell.
provider
Configured once and disclosed in review. Preferred default: an available OpenCode Go Flash model. If absent, the loop asks for configuration rather than substituting silently.
data leaving
Projection, referenced files, pending request — to the configured provider. Shown before the call, not after.
what is logged
Approved handoff text plus measurements, restricted local file, 30-day retention by default, opt-out available.
04 · the answer

Yes — the same chat can continue

pi hooks

Pi's context is a projection over a session file, not the file itself. Compaction appends a summary entry and rebuilds the window from it, while the entries it skipped stay stored. So “continue this chat, with a handoff as its memory” is a supported operation — not a workaround.

ACustom compaction — the workhorsebase context
// extension event, fired by /compact, threshold, or ctx.compact()
pi.on("session_before_compact", async (event) => ({
  compaction: {
    summary,                       // ← the approved handoff
    firstKeptEntryId: event.preparation.firstKeptEntryId,
    tokensBefore: event.preparation.tokensBefore,
  },
}));

The handoff becomes the summary Pi rebuilds context from. Same session file, same chat, same early scrollback — the live window starts at the handoff plus whatever tail you chose to keep.

BTree navigation with a summary — the precise cutcommand only
ctx.navigateTree(entryId, {
  summarize: true,
  customInstructions: /* the handoff */,
});

Walk back to an earlier point in the same session tree and summarize the branch you left. Same file, same chat; useful when the boundary is “the point before this side quest”. Being command-only, it can never fire from an event handler.

CNew session — the true blank windowcommand only
await ctx.newSession({
  parentSession: current,
  withSession: (c) => c.sendMessage(handoff, { triggerTurn: false }),
});

The cheapest possible first turn and a genuinely empty history — but persistence-without-a-turn and restoring the exact draft are the two joints still unproven in real Pi.

The distinction that matters: continuous chat rewrites what the model sees inside the same conversation. A new session changes which conversation exists. Same agent output, different promise — and, it turns out, very different risk.

Where the output goes, in each mode

pick one

Approval binds the exact text, the session file, the branch head, and the draft as it stands. Any drift invalidates it — including a single keystroke in the composer.

Which tail survives — the last N turns, or nothing — becomes a visible choice in the review, not a hidden constant. Pi's firstKeptEntryId is the mechanism.

One “context compacted” marker in the transcript. Everything above it is still scrollable, still searchable, still there.
5

It was in the editor the whole time. The hardest part of the new-session path — restoring it byte for byte — simply does not exist here.

06 · the consequence

Continuous mode removes the hardest joints

gate 0

The plan's four Gate 0 items were sized for the new-session path. Two of them stop existing when the loop stays in the same chat, one becomes a no-op, and only the judgement contract still has to be proven.

jointnew sessioncontinue this chat
Persist a handoff without triggering a turn unproven — needs a spike moot — compaction is Pi's own write path
Restore the exact pending draft unproven — the draft has to move moot — the draft never leaves the editor
Active 60% ask with a command-only switch unproven — command-only replacement reachable — compact() is base-context, approval is still required
Resumability and a link back needs proof — path existence isn't resumability inherent — omitted entries stay stored
A typed boundary + work-type verdict unproven unproven — unchanged, and still load-bearing
continuous chat buys+/−
No new-session plumbing, no draft restoration, no link to maintain.
The 60% ask becomes implementable without a command.
History stays one file, one id, one search surface.
continuous chat costs+/−
It is a projection rewrite inside the live conversation — a seam the human will see, in a chat they were reading.
A hand-written summary must keep Pi's file-tracking blocks, or read/edit state quietly drifts.
The system prompt and prior tool state are not re-primed the way a fresh session re-primes them.

My recommendation: ship continuous chat as the default destination and keep new session as the deliberate option for “this task is over, start another”. It satisfies the original requirement — a smaller, current context with continuity — while deleting the two joints most likely to fail, and it keeps the one promise a new session cannot make: the chat you were in is still the chat you are in.

07 · the rules

What holds in both modes

non-negotiable
approval
Neither mode runs without it. Compaction is capability, not consent — a boundary confirmation is still not a yes.
provider missing
Ask for configuration. Never substitute a different provider or model silently.
agent unavailable
Do not continue. Offer Pi's ordinary compaction as a separate choice, with its own approval.
transcript too large
Elide, never truncate mid-thought. Drop oldest turns first and say what was elided in the review.
unrunnable input
Refuse, don't flatten. Attachments and structured input that cannot be preserved stop the transition.
log write fails
Visible error, decision required. Block by default, with an explicit “continue without the audit record” path.
nothing approved
Nothing happens. The session, its branch and the draft are exactly where they were.

Still unproven, in both modes: the boundary verdict. Today's decision-server documentation covers tool events, and the plan requires a typed natural-boundary decision where an empty result can never be read as verified. Until that exists, the loop has a gate that only looks like a gate.
