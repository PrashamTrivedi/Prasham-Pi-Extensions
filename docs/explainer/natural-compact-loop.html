natural compact · loop design

The loop that earns a new session

A fresh session is the most powerful context reduction available — and the easiest way to lose a half-finished task. So the design isn't a compaction algorithm. It's a loop that has to be granted permission, three separate times, before it is allowed to cut.

01 — the pressure

Context doesn't rot by size. It rots by relevance.

Every turn stays in the window whether or not it still matters. Compaction shrinks the pile; it doesn't remove what's in it.

Pi's ordinary compaction rewrites the same conversation into a shorter form. What the plan reaches for is different in kind: start a new session that carries only what the next piece of work needs, and leave the old one intact and resumable underneath it.

That changes the unit of state from tokens to the session itself. Which is why the interesting problem isn't summarization — it's deciding when a cut is legitimate, and proving the cut lost nothing.

the framing that matters If the goal is "less irrelevant context", the loop's success condition is not a smaller window. It's work continuing after the cut with no loss the human can point at. The plan says this explicitly: continuity and usage are tracked together, and continuity comes first.
02 — the shape

Two loops, one seam

The plan's decisive constraint: newSession is command-only. The extension cannot begin the last step itself.

That one API fact splits the loop. An inner loop runs per turn: measure, gate, propose, adjudicate, offer. It is cheap, redundant, and produces nothing but a UI affordance. An outer chain runs only when a human commands it: generate, review, approve, switch, wait. Only the outer chain can cross the session boundary — and only after the human's own action.

This is the design I would hold the implementation to, because it makes the dangerous step unreachable by event handlers, timers, and model output.

03 — the actors

Four actors, four different hands

The loop's safety comes from a separation of powers, not from prompt instructions.

eyes · proposes

The running model

Reads the live branch and proposes two things: is this a boundary, and is the next work new or ongoing. Bounded call, bounded latency.

Can: propose. Cannot: approve, generate the handoff, or switch.
judge · verifies

Decision server → Jev

Answers verified, not_boundary, or uncertain with a work type and a reason. Decides when it and the model disagree.

Can: verify, classify, escalate. Cannot: consent. An empty result is silence, not a yes.
scribe · read-only

The handoff agent

A cheap model, configured once, producing the carry-over text. Read-only is a capability boundary, not a polite instruction: tool-free, or a restricted read interface.

Can: read the branch and bounded referenced files. Cannot: write, shell out, or claim a test ran.
authority · consents

The human

Holds four separate yeses: this boundary is real, this handoff is right, switch now, and — if offered — compact instead.

Can: edit everything, decline anything. Cannot: be replaced by an inferred intent.
why the separation is load-bearing No actor holds two powers. The model that wants to stop can't certify the stop; the judge can't write the handoff; the scribe can't switch; the human's boundary confirmation is not a switch approval. That's why every failure mode ends in "do nothing, say why" instead of "proceed carefully".
04 — the judgment

Only one verdict advances the loop

The most likely way to break this design is not a crash. It's a verdict that reads like permission.

Two rules do almost all the work here. First: a verdict is only evidence if the contract distinguishes "no matching decision" from "verified". An adapter returning {} is not a verified boundary — treating it as one converts a missing judgment into a green light.

Second: uncertainty is routed, not resolved. Unclear or disagreeing judgments escalate to the human as a boundary question. That question is asked using the same vocabulary as the loop, not as an approval prompt, so the human's answer cannot be laundered into a switch.

operable trap — try the empty verdict Selecting {} in the lab above is the whole argument for Gate 0's third investigation: the plan requires an explicit, typed boundary decision through decision-server before any of this is built. If only a generic verdict can be obtained, the loop's judgment gate is decoration.
05 — the knobs

What the cooldown is actually buying

After a decline, the loop must wait for both a new boundary and the configured cooldown. Two conditions, because either alone can be gamed by time passing.

Simulation of the loop's rules against a fixed boundary schedule and a steady context climb. It shows the trade the cooldown makes; it does not predict real usage.

Slide the cooldown to zero and the loop asks at every boundary it can — the fastest cut, at the price of interrupting a human who just said no. Slide it long and the context walks past 60% untouched, which is the pressure the feature exists to relieve. The plan proposes 15 minutes as a default and explicitly asks for that to be confirmed.

06 — the honest part

Four joints this loop rests on

These are the plan's Gate 0 items — each one either passes with observable evidence in real Pi, or the path stops and comes back for a scope decision.

J1

Persist a handoff without triggering a turn — plus the exact pending text

The upstream handoff example stages one combined draft. The plan needs the approved handoff saved as context with no model call, and the pending request separately restored to the editor, byte for byte.

If assumed: the handoff executes itself as a prompt, or the unsent request is flattened into a summary and the human's next action is gone.

J2

An active 60% ask at a settled boundary, with a command-only switch

An event handler may be able to present the question but cannot perform the replacement. The plan demands a real demonstration of the interaction before claiming the behavior.

If assumed: the requirement is silently downgraded to a notification, and the acceptance criteria pass on a behavior the human never agreed to.

J3

A typed boundary + work-type decision from decision-server through Jev

Today's documented decision contract covers tool events, not natural boundaries. It must return a distinguishable "no matching decision" and a real verdict, and the ownership and deployment of any adapter change sit outside this repository.

If assumed: an empty adapter result becomes a verified boundary, and the same model that wants to stop certifies its own stop.

J4

Resumability and linking of the old session

A path existing is not resumability. The plan requires a separate resume test to establish what can actually be guaranteed, and forbids switching when the original cannot be safely resumed and linked.

If assumed: the switch orphans the branch, and the "link to the old session" in every handoff template points at nothing.

07 — open decisions

Five things I'd want your call on

Each of these changes the loop's shape, not its styling. Recommendations are mine; the plan leaves them open on purpose.

Should the event loop be structurally unable to switch?

Yes. Inner loop ends at "offer"; only a command crosses the seam. This removes an entire class of bug rather than testing for it — and makes J2 a question about UX, not safety.

What exactly does an approval bind to?

A lease on a snapshot — handoff text, source session file, branch head, pending request. Any drift invalidates it and re-confirms; nothing is re-derived silently after the human reads it.

When is the handoff generated?

Lazily, only after the human opens review — so a declined ask costs nothing, and the scribe never runs on a session that was never going to move.

Cooldown default, and is a cooldown time or a boundary count?

15 minutes of wall clock, plus a new boundary identity. Time alone lets a busy session re-ask at the same cut; identity alone re-asks minutes later. Use the simulator above to sanity-check the number.

If the local handoff log can't be written, does the switch block?

Block by default, with a visible, dismissible error and an explicit "switch without the audit record" choice. Written records are a privacy commitment here; a silent failure breaks it before it breaks anything else.

The loop doesn't compact. It qualifies — boundary, judgment, consent — and only then is a fresh session allowed to exist.

Everything expensive in this design is downstream of that sentence: the two-loop split keeps the cut out of reach of an event handler, the separation of powers keeps each actor from certifying its own work, and the failure rules all resolve to "do nothing, say why".
