Pi mod pack · target architecture

How our Pi extensions will look

A Claude Code mod is a script the editor shells out to. A Pi mod is code inside the agent. That one difference is why the guard, the sidebar and the ledger can all read the same live state — and it is what every design decision below follows from.

01 The thing that changes

In Claude Code, a hook is a separate process. The editor serialises the event to JSON, writes it to the hook's stdin, waits for a payload on stdout, and reads the exit code. Everything the mod knows about the session has to arrive in that envelope, and everything it wants to do has to be expressible as a return value.

In Pi, an extensionA TypeScript module loaded into the Pi process. It registers tools, commands, renderers and event handlers against an ExtensionAPI. is loaded into the agent process. A handler is a function call. It can read the live event object, mutate it, replace a result, or refuse — and it shares memory with every other handler and with the UI.

One tool call, two worlds

Gotcha

Most of the plumbing in the harness's adapters/common.ts exists only because a hook is a subprocess: the once-guard that guarantees a single stdout payload, the deadline setTimeout, the always-exit 0, the neutral payload on every exception path, and a sha1 marker directory that de-duplicates an event delivered twice within 30 seconds.

That dedupe exists because Cursor loads both the plugin's hooks.json and the copy in ~/.cursor/hooks.json, so one event arrives twice. In-process there is one handler registration and no duplicate delivery — the whole mechanism disappears rather than being ported.

Insight

Because the UI and the guard share a process, a guard can react to something the UI already computed. for example, tightening itself as context fills up. In Claude Code those two things live in different processes and communicate by writing a file to disk and hoping someone reads it.

That particular guard is deferred (see §04), so this stays latent capability for now. It is worth knowing the architecture permits it — and worth knowing we are not building it yet.

02 Where a mod can reach in

One tool call passes through six points. Three of them let a mod change what happens; the others are observation. This is the whole design surface, and it is also the vocabulary the Jev adapter speaks — so the two things are worth learning together.

Step through a tool call

Jev verdictPi mechanismReach
denytool_call → { block: true, reason }stops the call
askno return value — the handler asks with ctx.ui.confirm(), then blocksstops it, conditionally

Gotcha

ask is the one verdict that does not survive translation as data. In Claude Code "ask the user" is a value returned up the hook protocol. Pi has no such return, so the handler has to do the asking and then decide whether to block. That means the adapter's supports() function can no longer be a static per-event table — it has to consult ctx.hasUI, because in a non-interactive run ask is unexpressible and a safety decision must degrade to a block instead.

The one that is genuinely new

The tool renderer is the capability with no Claude Code equivalent. A resolver runs for any tool name — including mcp__* names that are not registered yet, which is what happens on a resumed session before its MCP server has reconnected. Turn it on above and the same result renders as a table instead of a wall of JSON.

// one resolver, every tool, including ones not loaded yet
pi.registerToolRenderer((toolName, next) => {
  if (!toolName.startsWith("mcp__kshetra__")) return next();
  return {
    renderResult: (result, opts, theme) => new Text(toTable(result, theme)),
  };
});
Insight

next() returns whatever the remaining resolvers and then the tool itself would have used, so return next() is a clean fall-through and next() ?? mine only fills a gap. The resolver changes display only — it never gains access to the tool or executes it.

04 Where the numbers come from

This is the newest piece, and researching it turned up the one thing I had written off. The pattern is the same for every provider: account for tokens locally, per assistant message, and poll the provider for the number only it knows. Toggle between the two providers we report on.

Live provider usage

For opencode-go that number is a set of quota windows, and they are real. Pi's extension API exposes none — but the provider serves them over HTTP:

GET https://opencode.ai/zen/go/v1/usage
Authorization: Bearer $OPENCODE_API_KEY

{"usage":{"rolling":{"status":"ok","percent":2,"resetsAt":"2026-10-15T18:02:13.000Z"},
          "weekly" :{"status":"ok","percent":0,"resetsAt":"2026-10-19T00:00:00.000Z"},
          "monthly":{"status":"ok","percent":0,"resetsAt":"2026-11-15T12:17:12.000Z"}}}
Insight — this corrects something I had wrong

I had written "no 5h/7d quota display" as a non-goal, on the grounds that Pi exposes no rate-limit windows to extensions. That is true of Pi's API and false of the provider's. rolling resets hours out, weekly lands on a Monday, monthly on the 15th — the same shape as Claude Code's five_hour and seven_day windows, which the harness already reads.

So the pack can show real quota pressure after all. The general lesson: an extension's reach is the union of Pi's API and every API the machine can already reach. Pi not offering a number is not the same as the number not existing.

Gotcha

That endpoint is undocumented and unversioned — it is not part of OpenCode's published surface as far as I can find — and it returns percent only: no tokens, no spend. /zen/go/v1/models lists 37 models as {id, object, created, owned_by} with no pricing. So for opencode-go we show percent, reset times and locally-counted tokens, and no dollar figure. Estimating one from a price list we do not have would be inventing data.

It lives in one file behind a mapper, with the live payload as a test fixture, so a shape change fails loudly instead of rendering a wrong number.

The two providers are not symmetric

opencode-go has percent windows, no cost. Cloudflare Workers AI has the opposite: per-model token rates, a daily neuron allowance, and real month-to-date dollars from the billable-usage API — but no quota percentage. Both render through one ProviderUsage type, so the statusline and cockpit do not care which is active.

Deferred — gate and ramp

Both are out of this pass, and they were one system: workbench published an aggression value as context filled, and gate consumed it to decide how hard to push back. With no gate there is no consumer, so ramp is a number nothing reads. decorate goes with them — it toasts a denial, and without a gate there is nothing to toast; it comes back in the Jev phase, where shell-safety is a denial source.

The design is not lost. Two findings from it are worth keeping in view: Pi's built-in tools carry no annotations (only MCP resource tools declare readOnlyHint), so the conservative "assume the worst when hints are missing" default would make read prompt on every call; and the event-bus payload is typed unknown, so the ramp/gate pair silently disagreed on a channel name. Both are written up in docs/pi-mods-plan.md §2.

05 The Jev boundary — in-process

The harness was already built agent-neutral, which is why this port is small. Decisions live once, the engine is shared, and each agent gets a thin adapter with four functions. Adding Pi is a fourth case, not a rewrite. Decision: native only. Nothing in the pack shells out.

The path we rejected, and the one we keep

That table is the argument against the bridge. It reuses exactly the 94 lines of Claude-specific normalisation that the port exists to replace, while the 877 lines that matter are shared either way. So it saves almost nothing and inherits a subprocess spawn on every tool call, the output-shape matching, and the prompt stash.

Every subprocess removed

The same rule applies to the rest of the pack. These are the places a subprocess was going to appear, and what replaces each one. bun:sqlite below was verified working in-process before writing this.

Insight

Removing the sqlite3 shell-out is not only about process count. It also removes a PATH dependency and a per-render 1500 ms timeout that the cockpit ran inside its draw path — which is exactly the kind of thing that makes a panel feel slow. A read-only in-process handle is a single file open.

Unchanged by this port

Two things Pi cannot give the harness: a guaranteed transcript path (replaced by ctx.sessionManager.getBranch() plus ctx.getContextUsage()), and any schema enforcement on Jev's answers. screenshot-gate is inert because Pi has no built-in screenshot tool.

06 The shape, in one breath

Four extensions in one process over one shared library: usage fetches what the provider knows, workbench draws it, duck asks a second model for questions, and jev supplies the judgements — all over shared, which holds the config loader, branch-scoped state, the ProviderUsage type and the ledger reader. Nothing shells out.

extensions/
  usage/       opencode-go quota windows · Cloudflare neurons + MTD spend
  workbench/   pet · statusline (two-line footer) · cockpit (right overlay)
  duck/        /duck — nested model call, usage reported
  jev/         native adapter — runEvent() in-process, no execFile
  shared/      config · branch state · ProviderUsage · bun:sqlite ledger

  deferred:  gate · ramp · decorate   (see §04 and docs/pi-mods-plan.md §2)
The one sentence

A Pi mod is not a script the agent shells out to — it is code living inside the agent. So the footer, the sidebar and the ledger are the same program, nothing spawns a process, and the numbers on screen come from the provider's own API instead of from us estimating them.
